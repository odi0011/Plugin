# 可视化编辑器（visual-editor）

拖拽式页面搭建器。页面不是一段 HTML，而是「区块 → 栏 → 控件」的结构化文档；
样式是受白名单约束的键值对，由服务端编译成作用域 CSS。

## 为什么是结构化文档，而不是「直接改前台 HTML」

直接改渲染出来的 HTML 有两个绕不过去的问题：改动要按节点路径回写数据库源码，
页面结构一变路径就失配；样式要允许自由 CSS 文本，于是任何有内容权限的人
都能往页面里塞 `</style><script>`。

结构化文档把这两件事都变成了封闭集合：

- **样式**只能是 `VisualEditorSchema::styleProperties()` 里的属性，值必须过对应类型
  的校验（长度 / 颜色 / 枚举 / 比例 / 图片）。编译器生成选择器，用户碰不到。
- **HTML** 只有两个入口：`text` 控件的行内富文本、`html` 控件的结构片段。
  两者都走 `VisualEditorValue::sanitizeHtml()` 的标签白名单，`script` / `style` /
  `iframe` / `form` / `svg` 整棵删除，事件属性与伪协议链接一律剥掉。
- **视频**只接受「服务商 + 视频 ID」，iframe 地址由服务端拼。

结果是：最坏情况下文档 JSON 被写坏，页面上的元素不渲染，而不是给访客注入脚本。

## 三层结构与样式落点

```
文档 ── style[断点]
└─ 区块 section ── layout: boxed | full ── style[断点]
   └─ 栏 column ── width[断点] ── style[断点]
      └─ 控件 widget ── type + content[字段] ── style[断点]
```

每个元素有一个稳定 id（`ve` + 10 位十六进制），渲染成 `data-ve="<id>"`。
样式编译成 `.ve-doc-<文档id> [data-ve="<元素id>"] { … }`，因此：

- 样式与元素绑定，不依赖 DOM 路径，改结构不会让样式失配；
- 三个断点（桌面 / 平板 ≤1024px / 手机 ≤767px）用 `max-width` 媒体查询，
  小屏覆盖大屏，只在桌面设一次的属性自然向下继承；
- 复制元素会重新发一套 id——否则两份会共享同一条 CSS。

## 控件

标题、正文、图片、按钮、列表、引用、分隔线、留白、视频，以及自定义 HTML。
自定义 HTML 需要 `visual_editor.code` 权限，且**只有内容发生变化时**才检查这个权限
——否则降权之后连改标题都会被挡住。

新增控件类型只需要动 `src/Schema.php` 里的那张表：控件库、检查器表单、
API 参数校验、渲染分支都从它推出来。

## 前台路径

已发布文档挂在站点根下（`/about`），可在设置里加前缀（`/page/about`）。
接管发生在 `app.before_dispatch`，有四条前提：

1. 请求是 GET；
2. 路径不属于后台、`/api`、`/plugin-asset`、健康检查等保留空间；
3. 存在同 slug 且已发布的文档；
4. **核心内容（页面 / 文章 / 产品）没有占用同一个 slug——核心永远优先。**

第 4 条让「装了插件之后原有页面打不开」在结构上不可能发生。发布时如果检测到
核心已占用同名 slug，会直接拦下并提示改名。

优先级设为 20，排在维护模式（1）之后：站点维护中时维护页先赢。

前台页面 `extend` 的是核心前台布局，因此页头页脚、SEO、CSS 变量、全局 CSS/JS、
`frontend.*` 钩子、隐私同意条全部原样生效——站点改了页头，可视化页面跟着变。

## 三面对等与一处刻意的例外

`plugin.json` 的 `api` 段一条声明同时派生三面：`/api/v1/ext/visual-editor/<端点>`
路由、`ApiDoc` 契约、`AiAgentActionRegistry` 里的 Agent 动作。执行器统一是
`VisualEditorApi`，HTTP 与 Agent 网关共用核心的 `PluginExtApiController`，
因此参数白名单、scope 校验、权限求交、审批与审计只发生一次。

**例外：整棵文档树的批量保存不在公开 API 这一面。** 扩展 API 的参数是标量且每个
不超过 4KB，一棵完整的文档树装不进去。硬拆成 30 个参数分片只会换来一个又脆又
难用的接口。因此批量保存走后台编辑器自己的 CSRF 保护端点
（`/admin/visual-editor/save/{id}`），而公开 API 与 Agent 拿到的是等价的细粒度
操作：建文档、加区块、加控件、改内容、移动、删除、发布、回滚、列修订。
组合起来同样能从零搭出一整页，而且每一步都有独立的权限与审计记录。

这个例外由 `scripts/test_visual_editor_plugin_contract.php` 盯着：
理由必须写在代码里，两面必须汇到 `VisualEditorDocument` 的同一批写入方法上。

## 并发、修订与回滚

- 每次写入带 `lock_version` 乐观锁，并发保存返回 409 而不是互相覆盖；
- 每次改树先写一条修订，因此任何一步都能回滚；回滚本身也写修订，所以可以再回滚；
- 修订数按设置裁剪（默认 20，范围 3–100），不会无界增长。

## 编辑器为什么每次改动都请求服务端

画布是**服务端渲染**的：改动先落到内存里的文档树，再 POST 到
`/admin/visual-editor/render/{id}` 换回 HTML 与 CSS。代价是每个动作一次往返，
换来的是画布里看到的与前台输出的由同一段 PHP 生成——客户端没有第二套渲染器，
不会随时间慢慢走形。render 端点不落库，因此挪一个控件不会写一条修订。

服务端返回的是**归一化后**的树，客户端用它覆盖本地状态：被丢掉的非法值不会
留在界面上，避免「我明明设了但保存后没了」。

## 权限

| 权限点 | 用途 |
|---|---|
| `visual_editor.view` | 看列表、看轮廓、预览草稿 |
| `visual_editor.edit` | 建 / 改 / 删文档与结构 |
| `visual_editor.publish` | 发布与撤回 |
| `visual_editor.code` | 新增或修改自定义 HTML 控件 |

## 数据表

`plugin_visual_documents`、`plugin_visual_revisions`。

表名是**字面量**：插件迁移没有站点表前缀替换，所以运行时也只用字面表名
（`VisualEditorDocument::TABLE_*`），不走 `Database::table()`——后者会拼上站点前缀，
和迁移建出来的名字对不上。带表前缀的站点上这一点是功能正确性问题，不是风格问题。

卸载会 DROP 这两张表并清掉设置项。只想停用请用「停用」，那不会碰数据。
